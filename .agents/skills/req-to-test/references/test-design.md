# 测试设计方法指南

按需求类型选择测试设计方法，以及用例编写规范与优先级标准。维度矩阵回答「在哪些地方测」，设计方法回答「怎么设计一条用例」，错误推测清单是最后的兜底自查。

## 12 维度覆盖矩阵（测试点生成的强制框架）

生成测试点时，必须按以下 12 个维度逐一扫描。**每个维度的完成标准：至少有测试点覆盖，或显式标注「不适用+具体理由」**。「此需求不涉及」「应该没问题」不算有效理由。

| 组 | 维度 | 生成时机（流水线步骤） |
|---|---|---|
| A 功能正确性 | 1 正常功能流程 / 5 数据校验 / 6 状态流转 / 7 前后端交互 / 8 数据库一致性 | 第 3 步 |
| B 异常与边界 | 2 异常流程 / 3 边界值场景 | 第 4 步 |
| C 专项质量 | 4 权限控制 / 9 兼容性 / 10 性能风险 / 11 安全风险 | 第 4 步 |
| D 回归 | 12 历史缺陷可能复发点 | 第 4 步 |

### 1. 正常功能流程

- **目标**：每个功能点的主路径全部走通，每条业务规则的正向验证。
- **覆盖要点**：每个 R-xx 至少一条主流程用例；每条 BR-xx 至少一条正向验证；多步骤流程从入口走到终态（完整链路，不中途截断）；不同角色、不同入口（页面/分享链接/扫码）进入同一功能的正常路径。
- **常见坑**：只把「快乐路径」走一遍；漏掉角色差异导致的路径差异；不同入口漏测。

### 2. 异常流程

- **目标**：每个可能失败的分支都有明确的预期结果。
- **覆盖要点**：外部依赖失败（网络、短信网关、支付渠道）时提示与状态；用户操作中断（取消、返回、关闭页面）后能否恢复；校验失败后的提示文案与页面停留状态；请求超时后的表现与重试机制。
- **常见坑**：异常后状态残留（卡在中间态）；提示与实际不符；异常后数据不一致。

### 3. 边界值场景

- **目标**：所有带范围/长度/数量约束的值都测到边界。
- **覆盖要点**：数值上下界及 ±1（规则 1-100 必测 0/1/2/99/100/101）；字符串长度上下界及 ±1；数量边界（列表 0/1/N/上限）；时间边界（0 点、月末、闰年 2/29、时区切换）；次数限制临界（第 N 次成功、第 N+1 次拒绝，如验证码错误 5 次锁定）。
- **常见坑**：只测上限不测下限；忘了空集/空列表/空字符串；边界值未写明时列入澄清清单并用标注假设值。

### 4. 权限控制

- **目标**：每条「谁能做什么」的规则双向验证——有权的人能做、无权的人做不了。
- **覆盖要点**：角色×功能矩阵逐格验证（允许格 + 禁止格都要测）；**水平越权**（改 URL/参数中的 ID 访问他人数据）；**垂直越权**（普通用户直接调管理员接口）；权限变更即时生效（授权后立即可用、收权后立即失效）；无权限时各端 UI 表现（隐藏/置灰/报错需与需求一致）。
- **常见坑**：前端隐藏了按钮但接口没拦截（必须绕过 UI 直接调接口验证）；权限缓存导致收权后仍可操作；多端（App/Web/小程序）漏测某一端。

### 5. 数据校验

- **目标**：所有字段校验规则在后端同样生效（前端校验只是体验）。
- **覆盖要点**：绕过前端直接调接口验证每条规则；必填/格式/类型/长度/范围逐项；特殊字符（空格、emoji、`'"<>`、SQL/JS 注入串）；重复提交幂等性（连点、双开页面）；关联数据有效性（下拉选项的值被删后再提交）。
- **常见坑**：只测前端不测后端；空字符串 vs null vs 不传参三种情况表现不同；前后端校验规则不一致。

### 6. 状态流转

- **目标**：状态机全路径正确，非法跳转被拒绝。
- **覆盖要点**：每个合法迁移至少一条用例；**非法迁移**（跳过中间状态直接请求下一步操作）被拒绝；终态不可再操作；并发触发同一迁移（两人同时审批同一单据）；状态变化与所有展示点一致（列表、详情、消息推送、统计）。
- **常见坑**：状态变了通知没发；并发下状态跳跃；撤销/回退路径漏测；不可达状态或死状态未识别（发现即列入澄清清单）。

### 7. 前后端交互

- **目标**：接口契约与 UI 呈现一致，接口的各种返回前端都有处理。
- **覆盖要点**：四种 UI 状态（加载中/空数据/加载失败/无权限）都有预期；字段为 null/空串/undefined 时的展示；弱网/超时下的前端表现（防重复请求、按钮防连点）；列表分页、下拉刷新、上拉加载；错误码到用户提示文案的映射。
- **常见坑**：接口正常但字段类型变化导致前端崩溃；超时无任何提示；连点发出多个相同请求（重复下单）。

### 8. 数据库一致性

- **目标**：一次业务操作后，所有相关数据表同步正确。
- **覆盖要点**：主表+从表+冗余统计字段同步更新；操作部分失败时回滚完整（不留脏数据）；并发写入不丢数据不超卖；删除的级联处理（删主记录后从记录/引用是否合理）；软删数据不再出现在查询结果中。
- **常见坑**：只验证了 UI 没查库；统计报表与明细对不上；事务未回滚。
- **无 DB 权限时**：标注「需开发协助验证 SQL/数据」，降级为 UI + 接口返回双验证，不静默跳过。

### 9. 兼容性

- **目标**：声明支持的环境组合都可用。
- **覆盖要点**：浏览器矩阵（Chrome/Edge/Safari/Firefox 及版本下限）；移动端机型/OS 版本/分辨率；新旧版本共存（App 升级后老数据可读、本地缓存结构升级）；灰度发布期间两版本逻辑并行；第三方依赖（地图/支付 SDK）版本。
- **常见坑**：只测自己常用的浏览器；忘了低版本 OS 差异（API 兼容）；时区/语言环境影响展示。
- 需求未声明支持范围时，列入澄清清单，按团队基线假设并标注。

### 10. 性能风险

- **目标**：在合理数据量与操作频次下不出现明显劣化。（**做风险点识别，非专业压测**——识别出的风险移交专项压测并标注）
- **覆盖要点**：大数据量列表分页（万级数据）；批量操作上限（一次导入 10 万行）；高频操作（连点按钮、快速切换页签）；大文件上传下载；接口响应明显变慢的场景；前端长列表渲染、大图加载。
- **常见坑**：测试数据量太小测不出问题；无性能标准导致无法判定——需求没给指标时列入澄清清单。

### 11. 安全风险

- **目标**：常见风险点有基本防线。（**做风险点识别，非渗透测试**——识别出的风险移交安全专项并标注）
- **覆盖要点**：注入类（SQL 注入、存储型/反射型 XSS——输入点过滤 + 输出点转义都要看）；越权（与维度 4 联动，重点数据读取类接口）；会话（token 过期后的行为、登出后会话失效、多端登录策略）；敏感数据（日志/接口返回中的密码、手机号、身份证——脱敏规则、是否明文存储）；上传文件的类型与内容校验。
- **常见坑**：输入过滤了但输出没转义（存储型 XSS）；报错信息泄露内部实现（堆栈、SQL 语句）；内部接口无鉴权可直接调用。

### 12. 历史缺陷可能复发点

- **目标**：同类问题不在新需求中复发。
- **覆盖要点**：需求涉及模块的历史缺陷逐条映射为回归点；跨模块共用组件/工具类的历史缺陷同样要覆盖；**常见复发模式**清单自查——日期与时区处理、金额精度（浮点/分单位）、并发与幂等、缓存刷新（改了数据缓存没更新）、编码与特殊字符、空指针与未初始化。
- **无历史缺陷数据时**：标注「无历史缺陷数据，按常见复发模式检查」，按上述模式清单生成检查点；用户后续提供了缺陷库再补充。
- **常见坑**：只回归变更点不回归共用组件；新功能复用了带缺陷基因的老代码。

### 维度覆盖检查规则

- 完成标准：12 个维度每个「✅ 已覆盖（≥1 个测试点）」或「➖ 不适用（写明具体理由）」。
- 不适用必须具体到可核查：「纯文案调整无数据写入」可以，「不涉及」不行。
- 口头描述/会议纪要类输入往往缺非功能信息：兼容性、性能、安全维度的测试点基于本矩阵通用标准生成，并标注「需求未明确，按通用标准」+ 列入澄清清单。
- 覆盖状态汇总进《维度覆盖检查表》（模板见 `references/output-templates.md` 第 3 节），作为第 5 步审核材料；脑图与 Excel 交付物均携带维度信息。

## 接口测试设计要点（工作流 B 专用）

输入为接口文档时，用例按「正向 / 反向 / 边界 / 权限 / 幂等 / 并发」六类场景设计，同时映射到 12 维度矩阵（dimension 字段仍按 12 维度标注）。每类场景的用例模式与常见坑如下。

### 正向用例（正常功能流程）

- **每个接口的 happy path**：合法参数 + 合法认证 → 预期成功状态码（200/201/204）+ 业务码成功 + 响应字段完整、类型正确。**预期必须写具体**：状态码、业务码、关键字段值。
- **参数合法组合**：对每个字段的有效等价类取典型值；先逐字段覆盖（每字段取合法值），再补关键组合（相互约束的字段，如起止时间起<止）。
- **业务规则正向**：每条 BR-xx 的合法触发各一条（如「库存充足时下单成功」「金额>0 时创建支付单成功」）。
- **列表/分页接口**：默认参数正常返回、空数据返回合法空结构（`data: []` 而非报错）、分页字段正确。
- **响应结构校验**：断言响应字段的存在性、类型、枚举合法性、分页结构；不要只断言「返回成功」。

常见坑：只验证状态码不验证业务码与响应体；响应字段类型/枚举不校验；空列表接口误当异常。

### 反向用例（异常流程 + 数据校验）

- **参数非法**：类型错误（string 传数字）、格式错误（手机号传邮箱）、长度超限、范围越界、枚举值不存在 → 预期 400 或业务错误码
- **必填缺失**：缺必填参数、缺整个 body、body 为 null/空对象 → 400；**注意缺参、null、空串三者行为可能不同，分别验证**
- **认证失败**：无 token、token 过期、token 被篡改、签名错误 → 401，且不泄露内部信息
- **授权失败**：无权限角色调用 → 403（与权限用例区分：反向用例验证「规则不允许即拒绝」，权限用例重点测越权）
- **资源不存在**：查询/修改/删除不存在的 ID → 404 或业务码「记录不存在」
- **业务规则反向**：每条 BR-xx 的非法触发各一条（如「库存不足下单 → 业务码库存不足，订单未创建」）——**这是接口用例区别于纯参数测试的关键，必须逐条规则验证**
- **HTTP 方法错误**：GET 接口用 POST 调用 → 405；错误 Content-Type → 415
- **外部依赖失败**：依赖服务/数据库/消息队列不可用时接口行为（降级、超时、重试、报错码），需测试环境支持时标注「需模拟故障」

常见坑：只测参数不测业务规则反向；错误响应只验状态码不验错误码与提示文案；异常后数据是否写入（脏数据）未验证。

### 边界值场景（边界值 + 数据校验）

- **字段边界**：长度上下界 ±1、数值上下界 ±1、集合大小 0/1/N/上限、枚举边界
- **空值三态**：null / 空字符串 / 缺参——三种请求形态的响应差异必须分别验证
- **分页边界**：page=0、page=1、page 超出总页数、pageSize=0、pageSize 超上限、最后一页数据量、offset+limit 类参数同理
- **时间边界**：跨天/跨月/闰年 2/29、时区切换、时间格式（ISO8601 vs 时间戳）、起止时间相等、结束早于开始
- **字符边界**：Unicode、emoji、全角/半角、特殊字符（`'"<>`、% & 等 URL 编码相关）、超长字符串、SQL/JS 注入串（同时覆盖安全维度）
- **数值精度**：小数位、极大/极小值、浮点金额（分单位 vs 元单位）、精度丢失场景（同时覆盖历史缺陷维度）

常见坑：只测上限不测下限；忽略空串与 null 的差异；分页只测正常页。

### 权限场景（权限控制）

- **角色 × 接口矩阵**：列出所有角色与所有接口，逐格验证允许/禁止；至少覆盖：允许格 happy path、禁止格返回 403/业务码
- **水平越权**：把他人资源 ID 传入参数（如 `/order/{id}` 改用他人订单号）→ 403 或业务码，**不得返回他人数据**
- **垂直越权**：普通用户直接调用管理员接口 → 403；跳过前端直接发请求（防「前端隐藏但后端未拦截」）
- **token 生命周期**：过期后调用、登出后旧 token 调用、刷新 token 逻辑、多端登录策略
- **多租户隔离**：租户 A 的 token 访问租户 B 数据 → 403
- **无鉴权接口排查**：文档标注「需认证」的接口用无 token 调用必须 401——验证鉴权中间件确实生效

常见坑：只测 UI 层权限（前端隐藏按钮）不测接口；越权只测了一种方向；token 过期行为未测。

### 幂等场景（历史缺陷 + 数据校验）

- **重复提交**：同参数（含同幂等键）连续提交 N 次 → 结果一致、只产生一份数据、第二次起返回首次的结果或「已处理」业务码
- **幂等键**：相同 Idempotency-Key + 不同 body → 以首次为准或返回冲突；不同 key + 相同 body → 各自独立处理
- **重试场景**：模拟客户端超时后重发同一请求 → 不产生重复下单/重复扣款
- **天然幂等**：GET/查询/删除类接口重复调用结果一致；POST 创建类接口默认**不保证幂等**，需显式设计并验证（列表接口多次调用只追加一次等）
- **并发重复提交**：两请求同时到达同一资源 → 唯一约束/幂等键拦截，不产生双写

常见坑：幂等只验「重复调不报错」不验「不产生重复数据」；幂等键缺失时业务重复下单。

### 并发场景（状态流转 + 数据库一致性 + 性能风险）

- **并发创建同一资源**：唯一键（订单号/用户手机号/编号）冲突 → 一个成功一个 409/业务码，不产生脏数据
- **并发扣减**：库存/余额并发扣减 → 不超卖、不出现负数；用 N 个并发请求验证总额守恒
- **并发状态迁移**：同一单据并发审批/取消/发货 → 状态不跳跃、非法迁移被拒绝（与状态迁移法联动）
- **并发修改同一记录**：版本号/乐观锁/最后修改时间校验 → 后写者冲突报错，不静默覆盖
- **读改写一致性**：先读后写场景（读余额→扣减）并发时结果正确

并发用例的预期描述必须给出「N 个并发请求」的具体构造方式（用接口测试工具并发执行），标注是否需要测试环境配合（如多账号、多设备）。

### 接口错误码与响应校验（贯穿所有场景）

- 每个用例的 expected 至少含：**HTTP 状态码 + 业务码（如有）+ 关键响应字段断言**
- 状态码语义核对：200 成功 / 201 创建成功 / 204 无内容 / 400 参数错误 / 401 未认证 / 403 无权限 / 404 不存在 / 405 方法不允许 / 409 冲突 / 422 语义错误 / 429 限流 / 500 服务端错误
- 错误响应校验：错误信息可读、不含堆栈/SQL/内部路径（安全维度联动）；业务错误码与文档错误码表一致
- 响应字段校验：字段存在性、类型、枚举值、分页结构；null 字段的呈现方式（缺失 vs null）

### 接口用例 × 12 维度映射速查

| 用例场景 type | 主要维度 | 关联维度 |
|---|---|---|
| 正向 | 正常功能流程 | 数据校验（合法等价类） |
| 反向 | 异常流程 / 数据校验 | 数据库一致性（失败不落脏数据） |
| 边界 | 边界值场景 | 数据校验 |
| 权限 | 权限控制 | 安全风险（越权） |
| 幂等 | 数据校验 | 历史缺陷可能复发点、数据库一致性 |
| 并发 | 状态流转 / 数据库一致性 | 性能风险、历史缺陷可能复发点 |

## 方法选择规则

| 需求特征 | 首选方法 | 补充方法 |
|---|---|---|
| 输入字段带校验规则（长度/格式/范围/必填） | 等价类划分 + 边界值分析 | 错误推测 |
| 多个条件组合决定结果（如「会员且消费满 1000 且当月生日」） | 判定表 | 等价类 |
| 有明确业务流程（下单、审批、报销） | 场景法（路径覆盖） | 错误推测 |
| 有状态流转（订单状态、审核状态、账号状态） | 状态迁移法 | 场景法 |
| 多参数配置组合（浏览器×分辨率×支付方式） | 正交法或两两组合 | 输出说明组合覆盖范围 |
| 权限角色差异 | 角色矩阵法（角色×功能二维表逐格判断） | 边界值（越权访问） |

无论哪种需求，最后都叠加一轮**错误推测法**补充异常用例（见下文清单）。

## 各方法执行要点

### 等价类 + 边界值（字段级校验）

对每个输入字段建立提取表：

| 字段 | 有效等价类 | 无效等价类 | 边界值 |
|---|---|---|---|
| 示例：手机号 | 11 位合法号码 | 非数字、不足 11 位、超 11 位、空、含空格、特殊字符 | 10 位 / 11 位 / 12 位 |

- 边界值取：上点（正好等于边界）、内点（边界内典型值）、离点（边界外最近值）。
- 有明确范围时（如 1-100），必测 0、1、2、99、100、101。
- 规则未写明长度/范围时，列入澄清清单，先用合理假设值并标注。

### 判定表（条件组合）

1. 列出条件桩（所有影响结果的输入条件）与动作桩（所有可能输出）。
2. 每种条件组合成一列规则，逐列确定动作。
3. 条件数 >4 导致组合爆炸时，先合并等价规则（结果相同的无关条件列合并），仍过多时改用正交/两两组合并在产出中说明覆盖策略。
4. 判定表中的每列规则 = 至少一条测试用例。

### 场景法（流程覆盖）

1. 从流程图提取：基本流（主路径）、备选流（判断分支）、异常流（失败/中断路径）。
2. 每条「基本流+若干备选/异常流」的组合构成一个场景，命名格式：`场景x：<路径概述>`。
3. 覆盖要求：基本流必测；每条备选流至少被一个场景覆盖；每条异常流至少被一个场景覆盖。
4. 异常流不完整时（流程图缺异常出口），列入澄清清单并按常理假设（超时、失败、驳回）补齐，标注假设。

### 状态迁移法

1. 列出所有状态、触发事件、迁移后状态（画迁移表）。
2. 覆盖要求：每个合法迁移至少一条用例；重点测**非法迁移**（如在「已取消」状态下尝试发货）。
3. 检查是否有不可达状态或死状态（进得去出不来），发现即列入缺陷线索/澄清清单。

### 角色矩阵法（权限）

- 建二维表：行=角色，列=功能/操作，逐格标注「允许/禁止/无入口」。
- 用例覆盖：每格至少一条；重点测「禁止」格的越权访问（直接调接口/改 URL）。

## 错误推测清单（叠加使用）

对所有功能按此清单自查遗漏的异常用例：

- 空输入 / 全空格输入
- 超长输入（超过字段最大长度）、特殊字符（emoji、`'"<>`、SQL/JS 注入串）
- 重复提交（连点按钮、双击、并发下单）
- 网络异常（弱网、断网、请求超时后的重试）
- 数据不存在（查/改/删一条已不存在的记录）
- 数据冲突（两人同时编辑、库存并发扣减）
- 越权操作（普通用户访问管理员功能）
- 历史数据兼容（新规则上线后旧数据是否受影响）
- 分页边界（第 0 页、最后一页、超出总页数）
- 时间边界（跨天、跨月、闰年 2/29、时区）

## 优先级划分标准

| 级别 | 定义 | 典型内容 |
|---|---|---|
| P0 | 阻断核心业务，发布前必须全过 | 核心主流程（注册/登录/下单/支付）、资金相关、数据安全（越权/泄露）、数据丢失风险 |
| P1 | 主要功能缺陷会显著影响体验 | 高频功能的主逻辑、常用分支路径、主要异常处理 |
| P2 | 影响有限或低频 | 次要功能、边界值、罕见分支、提示文案错误 |
| P3 | 极低频或极端场景 | 兼容性组合、极端并发、罕见数据组合 |

分配规则：

- 一个模块的用例优先级呈金字塔分布（P0 最少但必须全过）。
- 用户故事/PRD 标注了优先级的，映射到对应层级后可微调。
- 拿不准时降不升（宁可 P0 里多一条，不可漏）。

## 测试用例编写规范

- **一条用例只验证一个测试点**。多个验证点拆成多条，编号相邻。
- **编号唯一且稳定**：TC-模块缩写-序号（如 TC-LOGIN-003），更新用例不改编号。
- **前置条件具体可构造**：写「已注册手机号 138xxxx 且未设置密码」，不写「有测试账号」。
- **操作步骤可执行**：每步一个动作，含具体测试数据；数据本身（账号、金额、字符串）写在步骤里而非口头说。
- **预期结果可判定**：写可观察现象（页面提示文案、跳转地址、数据库字段值、接口返回码），不写「功能正常」。
- **每条用例回链**：expected 字段之外，标注关联测试点（TP-xx）与需求（R-xx）。
- UI 用例含定位信息（页面/入口路径），接口用例含请求方法与路径（如有）。
