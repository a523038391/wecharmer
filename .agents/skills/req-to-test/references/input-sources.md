# 输入源处理指南

八种需求/接口输入类型的获取方式、信息提取清单与常见坑。处理任何输入前先通读对应小节。接口文档输入解析后走「工作流 B：接口文档驱动测试」。

## 1. PRD / 需求文档（链接或文件）

### 获取方式（按优先级尝试）

1. **公开链接**（无需登录即可访问）：直接用 WebFetch 抓取，让工具提取需求相关内容。
2. **平台文档链接**（飞书、腾讯文档、语雀、Confluence 等）：优先检查是否有对应连接器可用（如 feishu、tencent-docs），有则用连接器读取；无连接器或未授权时，进入下一步。
3. **兜底**：请用户将文档导出为 Word/PDF/Markdown 发到本地，或直接粘贴正文。不要反复重试无法访问的链接。

### 提取清单

- [ ] 需求背景与目标（为什么要做）
- [ ] 用户角色与使用场景
- [ ] 功能清单（模块 → 功能 → 子功能）
- [ ] 业务规则（逐条编号 BR-xx）
- [ ] 数据字典/字段说明（字段、类型、校验规则、必填性）
- [ ] 流程描述（文字版流程或引用的流程图）
- [ ] 交互/原型引用（PRD 中提到的原型链接或截图）
- [ ] 非功能需求（性能、兼容、安全）
- [ ] 版本号与变更记录（确认拿到的是最新版）

### 常见坑

- **版本过时**：PRD 链接指向旧版本，后续又有变更邮件/群消息。解析时向用户确认版本号与日期。
- **图片型 PRD**：整个 PRD 是长图。用多模态能力逐段读取，注意图片压缩导致的小字模糊处要标注「无法辨认，待确认」。
- **「待定」项**：PRD 中的 TBD/待定内容，全部收入澄清问题清单，不自行补全。
- **引用断裂**：PRD 引用了「详见 XX 文档」但拿不到时，列为缺失材料。

## 2. 原型图 / 设计稿

### 获取方式

- **图片文件**（png/jpg）：直接读取，逐屏分析。
- **Figma / MasterGo / 墨刀等链接**：需要对应连接器或用户导出截图；拿不到设计稿源文件时请用户提供导出图。
- **交互标注**：原型工具里的备注/标注常含关键校验规则，请用户一并导出。

### 提取清单

- [ ] 页面结构与导航关系（哪些页面、如何跳转）
- [ ] 字段清单：输入框、下拉、单选/复选，以及必填标记（*）、占位符提示（placeholder 常暗示格式要求）
- [ ] 按钮与操作：每个按钮触发什么、是否有二次确认
- [ ] 页面状态：空态、加载态、错误态、成功态、无权限态——缺哪态列哪态
- [ ] 提示文案：错误提示文案往往直接暴露校验规则（如「请输入 11 位手机号」）
- [ ] 数据展示与排序规则

### 常见坑

- 原型图上的文案≠最终文案，校验以规则为准、文案仅作线索。
- 交互细节（ loading 时长、防重复提交）常在备注里而非图上。
- 只给了 happy path 页面，异常态页面缺失——列入澄清清单。

## 3. 用户故事

### 结构识别

标准格式：「作为〈角色〉，我希望〈功能〉，以便〈价值〉」。伴随的验收标准常用 Given-When-Then（给定…当…则…）格式。

### 提取清单

- [ ] 角色（谁在用）
- [ ] 功能（做什么）
- [ ] 价值（为什么，用于判断优先级）
- [ ] 验收标准（每条 AC 直接映射为测试点；GWT 每条即一个测试场景）
- [ ] 隐含约束（故事中提到的角色权限、数据状态）

### 常见坑

- **无验收标准的故事**：只有故事没有 AC，是最常见的输入缺陷。将「请补充该故事的验收标准」列入澄清清单，同时基于常理给出建议版 AC 供确认。
- **粒度不一致**：有的故事是史诗级（一个故事顶一个模块），拆分后再分析。
- **多个故事重叠**：不同故事描述同一功能的不同侧面，先合并去重。

## 4. 需求变更说明

### 提取清单

- [ ] 变更编号/标题与提出时间
- [ ] 变更内容：改了什么（新增/修改/删除）
- [ **关键** ] 变更前基线：原来是什么。**只有「改成什么」没有「原来是什么」时，先索要旧版或让用户确认基线，无法获得则在影响分析中显式标注基线不明**
- [ ] 变更原因（影响回归范围判断）
- [ ] 影响版本与生效时间（是否涉及已上线功能）
- [ ] 数据兼容性（历史数据是否要迁移/清洗）

### 常见坑

- **隐性变更**：改了字段长度没提、改了接口没提。分析时主动检查上下游（接口、数据库、消息、报表）是否被牵连。
- **变更叠加**：多个变更说明针对同一模块，先按时间排序合并出最终态。

## 5. 会议纪要

### 提取清单

- [ ] 决定项：会上拍板的结论，注明「谁确认」
- [ ] 行动项：谁、做什么、什么时间点
- [ ] 待定项：标记为「下次讨论/待产品确认」的内容——这些是澄清清单的素材
- [ ] 需求描述：会中讨论的功能细节（常散落在对话里）

### 分类规则

提取出的每条信息标记为三档之一，不得混淆：

| 档位 | 含义 | 处理方式 |
|---|---|---|
| 已确认 | 会上明确拍板 | 直接进入需求模型 |
| 讨论中 | 有倾向但未拍板 | 列入澄清清单 |
| 临时想法 | 个别人提及、无讨论 | 列入澄清清单并标注来源 |

### 常见坑

- 纪要≠最终需求：重要结论需确认是否已落到 PRD；若 PRD 与纪要冲突，提示用户以哪份为准。
- 发言归属：区分「产品说」与「测试问」「开发答」，只有需求方的表述才进需求模型。
- 纪要常混入排期、人力等无关信息，过滤掉。

## 6. 产品口头描述

### 处理流程（与其他输入不同，必须先复述确认）

1. **原样记录**：先按用户原话整理成文字，不急于结构化。
2. **标记模糊点**：圈出「大概」「应该」「差不多」「之后再说」「先这样」等模糊表述，以及所有未被提及的异常分支、边界条件。
3. **结构化复述**：用自己的话把理解到的需求结构化复述给用户（功能点+规则+流程），请求确认或纠正。**复述确认通过后才能进入测试设计。**
4. **生成澄清清单**：所有模糊点与缺失项按优先级排序提问，一次问完，避免挤牙膏式追问。

### 常见坑

- 口头描述几乎必然缺失：异常分支、边界值、并发/重复操作、权限控制、历史数据兼容。这些缺失项要主动列入澄清清单，而非等用户想起来。
- 口头描述的需求范围会漂移（用户边说边改主意），每次复述确认时同时确认范围边界。

## 7. 业务流程图

### 获取方式

- **Mermaid / PlantUML 文本**：直接解析。
- **图片**（泳道图、BPMN、Visio 导出图）：多模态读取。
- **流程描述文字**：先画出流程图再分析（可用可视化工具向用户确认理解）。

### 提取清单

- [ ] 泳道/角色：每个环节由谁操作
- [ ] 节点类型：操作节点、判断节点（菱形）、开始/结束节点
- [ ] 判断节点的**完整分支条件**：每个菱形有几条出线，条件分别是什么
- [ ] 主路径（正常走通的全流程）
- [ ] 备选路径（判断节点的非主流分支）
- [ ] 异常路径（超时、驳回、取消、系统错误）
- [ ] 流程间的数据传递（上游产出什么给下游用）

### 常见坑

- **分支不全**：判断节点只画了 Yes 没画 No——缺的分支列入澄清清单。
- **异常路径缺失**：绝大多数流程图只画 happy path。主动询问每个可能失败的环节怎么处理。
- **条件表述模糊**：如「金额较大时需审批」——「较大」是多少？列入澄清清单。
- 流程图与 PRD 文字描述不一致时，标出冲突请用户裁决。

## 8. 接口文档 / API 文档

输入为接口文档时（无论是否伴随需求材料），优先走「工作流 B：接口文档驱动测试」。解析目标是产出**接口契约模型**（模板见 `output-templates.md` 第 9 节），**接口字段解析表是本输入类型的核心产出**。

### 获取方式（按优先级尝试）

1. **OpenAPI / Swagger**：JSON/YAML 文件直接解析；`/swagger-ui`、`/api-docs` 等在线端点用 WebFetch 或浏览器获取。解析出 paths、parameters、requestBody、responses、security、components/schemas。
2. **Postman / Apifox / 接口管理平台集合**：有导出文件（collection.json、Markdown、HTML）时读取；平台在线文档（Showdoc、YApi、Apifox 分享页）优先用对应连接器或 WebFetch。
3. **接口说明文档（Markdown/Word/Excel）**：直接读取，注意此类文档信息密度低，缺失项多。
4. **代码注释/源码定义**（用户可访问代码库时）：从路由定义、DTO/序列化类反推契约，标注「来源于代码，需与文档确认」。
5. **兜底**：请用户导出接口文档（导出 JSON/YAML 或粘贴接口清单），不要反复重试无法访问的链接。

### 提取清单（接口契约模型）

- [ ] 接口清单：接口名称、HTTP 方法、路径、所属模块、优先级、是否需认证（API-xx 编号）
- [ ] 请求头：Content-Type、Authorization 方式（Bearer/签名/无）、自定义头（X-Request-Id、幂等键）
- [ ] **请求参数（逐字段）**：字段名 | 位置（path/query/header/body）| 类型 | 必填 | 默认值 | 校验规则（长度/格式/范围/枚举）| 示例
- [ ] 响应结构：成功响应（HTTP 状态码、业务码、返回数据字段与类型、分页结构）；错误响应（错误码表、错误信息格式、是否含堆栈/内部信息）
- [ ] 认证与授权：各接口允许的角色/权限；无鉴权接口清单
- [ ] 业务规则（BR-xx）：接口行为背后的业务约束与状态流转（从文档描述、枚举取值、示例中反推）
- [ ] 幂等性：接口是否幂等、幂等键规则
- [ ] 限流/频率限制（如有）

### 常见坑

- **契约漂移**：文档版本与线上实现不一致（字段增减、校验变化）。解析时注意文档版本号与日期，必要时请用户确认哪个为准。
- **错误码表缺失**：只写了 200 成功，没写失败码——这是最常见缺陷。将「请提供错误码表/失败响应示例」列入澄清清单，先用通用 HTTP 语义（400/401/403/404/405/409/429/500）出用例并标注假设。
- **鉴权说明缺失**：没说哪些接口要登录、哪些角色可调——列入澄清清单，按「默认需认证」假设出用例并标注。
- **校验规则缺失**：字段有类型没长度/范围/格式——列入澄清清单，边界用例用合理假设值并标注。
- **响应字段类型不明确**：`data` 是对象还是数组、是否可能为 null——影响响应校验用例与前后端交互维度，逐项标注待确认。
- **URL 模板未展开**：`/users/{id}` 未说明 id 的格式与取值范围——等价类划分的依据缺失，列入澄清清单。
- **枚举/字典未给全**：状态字段的可取值是业务规则与状态流转用例的输入，缺枚举值时按文档示例反推并标注。
- **OpenAPI 大文件**：接口很多时按模块分批解析，先出契约模型再逐模块出用例，避免一次生成过载。

## 多源输入合成规则

同时收到多种输入时：

1. 每种输入独立解析完毕后，先做**交叉比对**：同一功能点在不同材料中的描述是否一致。
2. 冲突时按权威度取值：正式 PRD > 变更说明（针对变更部分）> 会议纪要已确认项 > 原型图 > 用户故事 > 口头描述。**接口文档与 PRD 冲突时**（PRD 描述的业务行为 vs 接口文档的校验/返回值），以接口文档为接口契约事实、以 PRD 为业务意图基准，冲突项列入澄清清单请用户裁决。
3. 缺口互补：原型图提供的字段校验、流程图提供的分支、纪要提供的决定项、接口文档提供的接口契约，合并进同一个需求模型。
4. 向用户汇报合成结果时，注明每个需求点的信息来源（如「R-03 来源：PRD v2.1 + 3/12 纪要」）。
5. 接口文档 + 需求材料同时存在时：先用工作流 B 解析接口契约与生成接口用例，再用工作流 A 的 12 维度矩阵补需求侧场景（兼容性、安全、历史缺陷等），两套用例合并交付。
