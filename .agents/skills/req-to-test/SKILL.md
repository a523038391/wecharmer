# req-to-test — 多源需求 / 接口文档转测试分析（根据需求生成用例）

## 概述

将测试人员收到的输入统一解析后，按固定流水线产出测试资产。按输入形态走两条流水线：

- **工作流 A（多源需求）**：PRD 文档、原型图、用户故事、需求变更说明、会议纪要、产品口头描述、业务流程图
- **工作流 B（接口文档）**：接口文档 / API 文档（OpenAPI/Swagger、Postman 集合、接口说明文档等）

核心价值：不管输入以什么形式、什么质量到达，都执行同一套可靠的测试分析流程；测试点生成受**12 维度覆盖矩阵**强制约束（正常功能流程 / 异常流程 / 边界值场景 / 权限控制 / 数据校验 / 状态流转 / 前后端交互 / 数据库一致性 / 兼容性 / 性能风险 / 安全风险 / 历史缺陷可能复发点），每个维度必须覆盖或显式声明不适用；最终产物为可直接用 XMind 打开编辑的测试用例脑图（含维度覆盖检查视图）与结构化用例 JSON（可导出 Excel、可交接接口自动化）。

## 工作流 A：多源需求转测试分析（六步）

### 第 1 步：需求输入获取与解析

逐项识别用户提供了哪些输入，按类型解析。每种类型的获取方式、提取清单与常见坑见 `references/input-sources.md`：

| 输入类型 | 获取方式 |
|---|---|
| PRD/需求文档链接 | 公开链接用 WebFetch；飞书/腾讯文档等优先用对应连接器；无法访问时请用户导出或粘贴 |
| 原型图/流程图图片 | 直接读取图片（多模态能力），提取页面元素、交互、字段、流程分支 |
| 用户故事 | 识别「作为…我希望…以便…」结构，提取验收标准 |
| 需求变更说明 | 提取变更前后差异；缺少旧版本基线时先向用户索要 |
| 会议纪要 | 提取需求相关决定项、行动项，区分「已确认」与「待定」 |
| 产品口头描述 | 原样记录，标记模糊点，进入澄清流程 |
| 业务流程图 | 提取泳道、主路径、分支条件、异常路径，用于场景法设计 |
| 接口文档 / API 文档 | 见 `references/input-sources.md` 第 8 节；解析后**转工作流 B**，不进入本工作流 |

解析规则：

- 材料不足时，明确列出还缺什么，不编造需求内容。
- 同一需求有多份材料时，以最新日期/最高权威为准（正式 PRD > 会议纪要 > 口头描述），冲突点单独标出。
- 解析完成后，向用户简述已提取到的需求概要，确认理解无误再继续。

### 第 2 步：提取业务规则（需求结构化建模）

将解析结果写入需求模型，**业务规则清单是本步核心产出**（第 3 步的测试点直接由规则推导）：

- 功能点清单（R-xx 编号，模块/功能/子功能，含优先级）
- **业务规则清单（BR-xx 编号）**：每条规则一句话、可独立验证，覆盖输入校验、流程约束、权限控制、状态流转、计算逻辑五类
- 数据字段（字段、类型、校验规则、必填性、边界值）
- 业务流程（入口、步骤、分支条件、异常出口）
- 角色与权限
- 非功能需求（性能、兼容、安全，如有）

同步生成《需求澄清问题清单》（模板见 `references/output-templates.md`）：规则表述含糊（「较大」「合理」「尽快」）、预期结果不可判定、字段校验规则缺失、流程异常分支缺失、多材料冲突的，全部列入，向用户呈现并等待回答；用户表示「先按现有信息出」时，所有假设显式记录在产出的「假设与待确认」章节，不得静默假设。

### 第 3 步：按维度矩阵生成测试点

测试点生成受 **12 维度覆盖矩阵**强制约束（每个维度的覆盖要点、典型测试点模式与常见坑见 `references/test-design.md`）。本步先覆盖「功能正确性组」5 个维度，第 4 步补全其余 7 个：

| 步骤 | 覆盖维度 |
|---|---|
| 第 3 步（本步） | 正常功能流程、数据校验、状态流转、前后端交互、数据库一致性 |
| 第 4 步 | 异常流程、边界值场景、权限控制、兼容性、性能风险、安全风险、历史缺陷可能复发点 |

从业务规则逐条推导测试点（设计方法选择规则见 `references/test-design.md`）：

- **每条业务规则至少映射一个正常场景测试点**（规则生效的正向验证，覆盖「正常功能流程」维度）
- 逐维度扫描推导：输入/输出字段 → 数据校验维度；有状态字段的功能 → 状态流转维度；页面与接口交互 → 前后端交互维度；涉及写库的操作 → 数据库一致性维度
- 方法映射：输入校验 → 等价类+边界值；条件组合 → 判定表；业务流程 → 场景法；状态流转 → 状态迁移法；权限差异 → 角色矩阵法
- 测试点编号 TP-xx，每条标注：覆盖维度、设计方法、优先级（P0-P3）、关联 BR-xx/R-xx

### 第 4 步：补充异常、边界与专项维度

对已有测试点逐维度补漏，直至 12 维度全部覆盖或显式声明不适用：

- **异常流程维度**：每个外部依赖失败（网络/网关/支付渠道）、每个用户操作中断（取消/返回/关闭）、每个校验失败的提示与后续状态、超时与重试
- **边界值场景维度**：带范围/长度/数量的字段，补上点/内点/离点测试点；数量边界（0/1/N/上限）、时间边界（跨天/月末/闰年/时区）
- **权限控制维度**：角色×功能矩阵逐格验证；水平越权（改 ID 访问他人数据）、垂直越权（直接调管理员接口）；权限变更后即时生效
- **兼容性维度**：声明支持的浏览器/机型/OS 组合；新旧版本数据兼容
- **性能风险维度**：大数据量（列表分页/导入导出）、高频操作（连点/快速切换）、大文件、慢接口（识别风险点即可，专业压测另行标注移交）
- **安全风险维度**：注入类（SQL/XSS）、会话与 token、敏感数据脱敏与泄露（识别风险点即可，深度渗透另行标注移交）
- **历史缺陷可能复发点维度**：用户提供了历史缺陷数据的，逐条映射回归点；没有的按常见复发模式检查（日期时区、金额精度、并发、缓存刷新、编码字符、幂等）并标注「无历史数据，按模式检查」
- 每个补充测试点标注覆盖维度；错误推测清单（见 `references/test-design.md`）作为兜底自查

**维度覆盖完成标准**：12 个维度每个都有测试点，或显式标注「不适用+具体理由」（如「纯样式调整，无数据写入」→ 数据库一致性不适用）。完成后生成《维度覆盖检查表》（模板见 `references/output-templates.md` 第 3 节），作为第 5 步审核材料。

### 第 5 步：测试人员审核、筛选、补充（人工检查点）

- 向测试人员完整呈现：业务规则清单 + 全部测试点（按 12 维度分组，含优先级、设计方法、关联规则）+ **维度覆盖检查表**（12 个维度的覆盖状态与缺口）+ 澄清问题清单
- 审核重点：维度覆盖检查表中「⚠ 未覆盖」的维度——测试人员决定补测试点、还是确认「不适用」（须给具体理由）
- 由测试人员：删除不需要的、合并重复的、补充遗漏的、纠正理解偏差的、回答澄清问题
- 按反馈更新后再次呈现，**未获测试人员明确确认前，不得进入第 6 步**
- 本步可多轮迭代，测试人员说「确认」「可以」「就这样」等才视为通过

### 第 6 步：形成测试用例 xmind 并导出

1. 将确认后的内容组织为脑图树 JSON（结构规范与示例见 `references/output-templates.md` 第 7 节）。层级固定：**根（需求名）→ 模块 → 测试点 → 用例**；用例节点必填 priority，覆盖维度作为标签，前置条件/操作步骤/预期结果写入 note
2. 调用 `scripts/testcase_to_xmind.py` 生成 .xmind 文件（P0-P3 自动映射为 XMind 优先级图标；`--format md` 可输出 Markdown 大纲作为通用备选）。传**用例集 JSON**（含 `cases` 数组）时会生成双 sheet：**「按模块」**视图 + **「维度覆盖」**视图——后者固定列出 12 个维度分支、每维度下的用例数，空维度挂「⚠ 未覆盖」警示节点，供审核维度缺口
   - **默认 `--detail-style topics`**：前置条件 / 操作步骤 / 预期结果展开为**子主题**（操作步骤每条一个子节点），脑图展开即可审阅；若需紧凑版，加 `--detail-style note` 折叠进节点便签
3. 同时需要 Excel 交付时：用例集按 `references/output-templates.md` 第 5 节 JSON Schema 组织，调用 `scripts/testcase_to_xlsx.py`（含「覆盖维度」列，概要 sheet 含维度覆盖统计）
4. 交付物（.xmind / .xlsx）放当前工作目录，中间 JSON 放临时目录

## 工作流 B：接口文档驱动测试（六步）

输入为接口文档 / API 文档（或用户明确要求「按接口文档出用例」）时走本流水线，产出**接口测试用例**。流程（对应七个环节，「接口文档获取」并入第 1 步）：

**接口文档 → 解析接口字段 → 生成正向用例 → 生成反向用例 → 补充边界、权限、幂等、并发场景 → 测试人员审核业务规则 → 沉淀接口测试用例**

设计要点（正向/反向/边界/权限/幂等/并发的用例模式与常见坑）见 `references/test-design.md`「接口测试设计要点」章节；各步模板见 `references/output-templates.md`。

### 第 1 步：解析接口文档与接口字段

按 `references/input-sources.md` 第 8 节获取并解析接口文档，产出**接口契约模型**（模板见 `references/output-templates.md` 第 9 节）：

- **接口清单**（API-xx 编号）：接口名称、HTTP 方法、路径、所属模块、优先级、认证要求
- **请求头**：Content-Type、Authorization、自定义头（X-Request-Id、幂等键等）
- **请求参数**：路径参数 / 查询参数 / 请求体参数，逐参数记录——字段名、位置、类型、必填、默认值、校验规则（长度/格式/范围/枚举）、示例值
- **响应结构**：成功响应（HTTP 状态码、业务码、返回数据结构与字段类型）、错误响应（错误码表、错误信息格式）
- **认证与授权**：认证方式（无认证 / Bearer token / 签名 / 白名单）、角色权限要求
- **业务规则**（BR-xx）：接口语义背后的业务约束（如「金额必须大于 0」「库存不足下单失败」「已支付订单不可取消」）
- **幂等性**：接口是否幂等、幂等键规则（如 Idempotency-Key）
- **频率限制**：限流阈值（如有）

解析规则：

- 文档缺失部分（错误码表、鉴权说明、字段校验规则、边界值）逐项列入《需求澄清问题清单》，不编造。
- 接口字段解析表逐字段列出：**字段名 | 位置（path/query/header/body）| 类型 | 必填 | 校验规则 | 边界值 | 示例**，这是第 2-4 步生成用例的直接依据。
- 与业务规则冲突的接口约束（如文档允许负数但业务规则禁止）单独标出，交第 5 步审核。
- 解析完成后向用户简述接口概要（接口数、模块划分、认证方式），确认理解无误再继续。

### 第 2 步：生成正向用例

每个接口的合法路径全覆盖，作为「正常功能流程」维度主用例：

- **happy path**：合法参数 + 合法认证 → 预期成功状态码（200/201/204）、业务码成功、响应字段完整且类型正确
- **参数合法组合**：对每个字段的有效等价类取典型值组合（先单字段覆盖，再关键组合覆盖）
- **业务规则正向**：每条 BR-xx 的合法触发路径各一条用例（如创建订单成功、库存充足时扣减成功）
- **分页/列表接口**：正常分页、默认参数、空数据列表（响应为合法空结构而非报错）

### 第 3 步：生成反向用例

每个接口的失败路径覆盖，作为「异常流程」「数据校验」维度主用例：

- **参数非法**：类型错误、格式错误、长度/范围越界、枚举值不存在
- **必填缺失**：缺必填参数、缺整个 body、body 为 null
- **认证失败**：无 token、token 过期/无效/被篡改 → 401
- **授权失败**：无权限角色调用 → 403（与第 4 步权限用例互补）
- **资源不存在**：查询/修改/删除不存在的 ID → 404 或对应业务错误码
- **业务规则反向**：每条 BR-xx 的非法触发各一条（如库存不足下单 → 业务码「库存不足」）
- **HTTP 方法错误**：错误 method 调用 → 405
- **请求头错误**：Content-Type 不匹配、缺自定义头 → 400/415

### 第 4 步：补充边界、权限、幂等、并发场景

对已有用例按四类场景补漏（用例模式与常见坑见 `references/test-design.md`）：

| 场景 | 覆盖要点 |
|---|---|
| **边界值** | 字段长度/数值/集合大小边界（上点/内点/离点）；**空值三态**（null / 空字符串 / 缺参）行为差异；分页边界（page=0、超上限、末页）；时间边界（跨天/月末/闰年/时区）；Unicode/emoji/特殊字符/注入串 |
| **权限** | 角色 × 接口矩阵逐格验证；**水平越权**（改 ID 访问他人数据）；**垂直越权**（低权限调高权限接口）；token 过期/登出后调用；多租户数据隔离 |
| **幂等** | 同参数重复提交 N 次结果一致、不产生重复数据；幂等键（相同 key 不同 body）；超时后客户端重试；GET/查询类天然幂等、POST 创建类需显式验证 |
| **并发** | 并发创建同一资源（唯一约束冲突）；并发扣减库存/余额（不超卖）；并发状态迁移（重复审批同一单据）；并发修改同一记录（乐观锁/版本号）；读改写一致性 |

非接口场景（兼容性/性能/安全/历史缺陷）按工作流 A 第 4 步的 12 维度矩阵补漏：URL 版本兼容与响应字段兼容 → 兼容性；大数据量分页、批量接口、限流阈值 → 性能风险；注入、敏感数据脱敏、鉴权缺失 → 安全风险；金额精度、幂等、并发等 → 历史缺陷可能复发点。完成后生成《维度覆盖检查表》。

### 第 5 步：测试人员审核业务规则（人工检查点）

- 向测试人员完整呈现：**接口契约模型**（含接口字段解析表）+ 业务规则清单 + 全部测试点（按 12 维度分组）+ 维度覆盖检查表 + 澄清问题清单
- 审核重点：
  - **接口语义与业务规则的绑定是否正确**（接口行为是否符合业务规则，用例的预期结果是否即业务规则要求的产出）
  - 维度覆盖检查表中「⚠ 未覆盖」的维度——补用例或确认「不适用（写明理由）」
  - 澄清问题回答（错误码、鉴权、边界值、幂等键等）
- 由测试人员：删除、合并、补充、纠正；**未获明确确认前不得进入第 6 步**；可多轮迭代。

### 第 6 步：沉淀接口测试用例

1. 将确认后的用例组织为**接口用例集 JSON**（schema 见 `references/output-templates.md` 第 10 节）：每条用例含 method / path / headers / body / expected_code / response_checks 等接口字段，`dimension` 标注覆盖维度；type 标注「正向 / 反向 / 边界 / 权限 / 幂等 / 并发」场景
2. 交付方式（按需组合）：
   - 调用 `scripts/testcase_to_xlsx.py` 生成 Excel（含请求方式/路径/请求头/请求参数/预期状态码/响应校验列 + 维度覆盖统计 sheet）
   - 调用 `scripts/testcase_to_xmind.py` 生成脑图（用例集输入自动生成「按模块」+「维度覆盖」双 sheet）
   - Markdown 用例文档
3. 接口用例集 JSON 可直接交接**接口自动化执行**（如结合 api-test-automation 类技能生成 pytest+requests 脚本），JSON 即沉淀资产，保证分析结果可复用
4. 交付物（.xmind / .xlsx / .md / cases.json）放当前工作目录，中间 JSON 放临时目录

### 典型提示词模板：资深接口测试工程师 · 15 场景全覆盖

用户按以下模板提问（或其变体）时走本快速通道，模板如下：

> 你是一名资深接口测试工程师，请根据以下接口文档生成接口测试用例。
> 请覆盖：1. 正常请求 2. 必填参数缺失 3. 参数为空 4. 参数类型错误 5. 参数长度边界 6. 枚举值非法 7. token 缺失 8. token 过期 9. token 无权限 10. 数据不存在 11. 重复提交 12. 幂等性 13. 并发请求 14. 业务状态不允许 15. 返回字段校验
> 请用表格输出：用例编号、测试场景、请求方法、请求路径、请求参数、前置条件、预期状态码、预期返回、优先级。

处理规则：

1. **场景清单已由用户指定**：15 个场景即覆盖要求，直接映射到六类用例场景（下表），**不再向用户确认场景范围**；但第 1 步契约解析与第 5 步审核仍照常执行，文档缺失照旧列入澄清清单。
2. **15 场景 → 用例场景（type）映射表**：

| # | 提示词场景 | type | 对应步骤 | 设计要点（详见 test-design.md） |
|---|---|---|---|---|
| 1 | 正常请求 | 正向 | 第 2 步 | happy path：合法参数+合法认证 → 成功状态码+业务码+响应字段完整 |
| 2 | 必填参数缺失 | 反向 | 第 3 步 | 缺必填参数 / 缺整个 body / body=null → 400 或业务码 |
| 3 | 参数为空 | 反向/边界 | 第 3、4 步 | **空值三态**：null / 空字符串 / 缺参，分别验证行为差异 |
| 4 | 参数类型错误 | 反向 | 第 3 步 | string 传数字、数字传对象、类型不符 → 400 |
| 5 | 参数长度边界 | 边界 | 第 4 步 | 长度上下界 ±1；数值范围/集合大小边界同理 |
| 6 | 枚举值非法 | 反向 | 第 3 步 | 枚举不存在、大小写不符、数字型枚举传负数 |
| 7 | token 缺失 | 反向 | 第 3 步 | 无 token / 无 Authorization 头 → 401 |
| 8 | token 过期 | 权限 | 第 4 步 | 过期 token、登出后旧 token、被篡改 token → 401 |
| 9 | token 无权限 | 权限 | 第 4 步 | 低权限角色调高权限接口 → 403；水平越权（改他人资源 ID）|
| 10 | 数据不存在 | 反向 | 第 3 步 | 查询/修改/删除不存在的 ID → 404 或业务码「记录不存在」|
| 11 | 重复提交 | 幂等 | 第 4 步 | 同参数连续提交 N 次 → 只产生一份数据；验证「不产生重复数据」而非只验不报错 |
| 12 | 幂等性 | 幂等 | 第 4 步 | 幂等键机制：相同 key+不同 body、不同 key+相同 body、超时重试 |
| 13 | 并发请求 | 并发 | 第 4 步 | 并发创建唯一冲突 / 并发扣减不超卖 / 并发状态迁移；预期写明「N 个并发」构造 |
| 14 | 业务状态不允许 | 反向 | 第 3 步 | 状态流转非法（已支付不可取消、已审核不可再审）→ 业务码；与状态迁移法联动 |
| 15 | 返回字段校验 | 正向 | 第 2 步 | 响应断言：字段存在性、类型、枚举合法性、分页结构；**不只断言「返回成功」** |

3. **场景去重**：11「重复提交」与 12「幂等性」语义不同——前者无幂等键、靠后端防重/唯一约束拦截，后者基于显式幂等键（Idempotency-Key / X-Request-Id）机制，**分别设计用例**，不可合并。
4. **编号约定**：仍按接口分模块 `TC-<MODULE>-NNN`；15 个场景每个至少一条用例，接口不适用的场景（如无权限体系、纯查询无创建）在维度覆盖检查表注明「不适用+理由」。
5. **表格输出**：用户要求「用表格输出」时，按 `references/output-templates.md` 第 10 节「9 列表格模板」直接交付 Markdown 表格；**同时仍产出接口用例集 JSON**（9 列表格是其快捷视图，JSON 才是沉淀资产，可导出 xlsx/xmind、交接自动化）。

## 特殊流程：需求变更影响分析

输入是变更说明时，除标准流程外必须输出：

- **变更内容摘要**：改了什么、为什么改
- **影响面分析**：直接影响的模块、间接影响（上下游功能、共用组件、历史数据）
- **测试资产影响**：需新增的用例、需更新的用例（列编号）、可废弃的用例（列编号）
- **回归范围建议**：最小回归集 / 完整回归，并给出选择理由

## 输出规范

- 所有编号稳定且唯一：需求 R-xx、业务规则 BR-xx、接口 API-xx、测试点 TP-xx、用例 TC-xx，便于追踪引用。
- 一条测试用例只验证一个测试点；步骤可执行、预期结果可判定。
- **12 维度覆盖矩阵是测试点生成的强制框架**：每个测试点标注所属维度；每份用例产出附维度覆盖检查表；维度不适用必须写明具体理由。
- 接口用例除维度外，标注 **type 场景**（正向/反向/边界/权限/幂等/并发），并携带 method / path / headers / body / expected_code / response_checks 等接口字段，保证可直接执行与交接自动化。
- 所有产出使用中文撰写。
- .xmind 文件必须由脚本生成（不手工构造 zip），xlsx 同理。
- 脑图层级固定：需求 → 模块 → 测试点 → 用例；覆盖维度作为用例标签；P0-P3 映射 XMind 优先级图标；用例集 JSON 生成的脑图含「维度覆盖」第二 sheet。
